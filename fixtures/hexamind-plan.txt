# HexaMind — 六帽思维智能体群聊插件

**产品需求文档（PRD）与技术实施计划书**

版本：v1.0\
目标宿主：DeepSeek Harness（DSH）\
开发方式：Codex 辅助开发、开源项目复用、独立插件发布\
产品形态：可安装、可卸载、可配置的 Harness 插件\
项目暂定代号：`hexamind`

---

## 1. 项目概述

### 1.1 产品介绍

HexaMind 是一款基于六种思维模式构建的 AI Bot 群聊插件。

插件预设六个拥有独立身份、思考规则、行为边界和模型配置的 AI Bot：

- 白帽：事实与证据
- 红帽：直觉与情绪
- 黑帽：风险与批判
- 黄帽：价值与机会
- 绿帽：创新与替代方案
- 蓝帽：组织与元认知管理

用户可以像使用微信一样与六个 Bot 聊天，通过 `@白帽`、`@黑帽` 或 `@全体` 选择需要参与的角色。

每顶帽子的思维职责由插件定义，不依赖特定模型。用户无需配置六个不同的大模型，只要 DeepSeek Harness 已有一个可用模型，即可运行整个系统。

用户也可以为每顶帽子单独绑定 Grok、DeepSeek、Kimi、Gemini 等已接入模型。

插件通过 Harness 的统一模型管理能力，兼容第三方 API 和免费模型插件。

### 1.2 产品核心理念

**角色决定如何思考，模型决定由谁执行思考。**

三个重要原则：

1. 六帽身份与底层模型完全解耦。
2. 人类用户拥有最高讨论控制权。
3. 系统的目标是提高思考和决策质量，而不是单纯增加 AI 回复数量。

### 1.3 项目目标

建立一套能够长期使用、自由调用、结构化协作的思维辅助系统。

第一版必须实现：

- 安装插件后自动创建六个默认思维 Bot。
- 支持个人与单个 Bot 私聊。
- 支持微信群聊式多人 Bot 对话。
- 支持 `@` 调用单个、多个和全部 Bot。
- 每个 Bot 内置独立思维策略。
- 默认继承 DeepSeek Harness 当前模型。
- 支持为每个 Bot 独立指定模型。
- 支持使用 Harness 中其他插件注册的模型。
- 支持人工主持和 AI 蓝帽辅助主持。
- 支持聊天记录持久化、讨论暂停与终止。
- 支持将完整讨论整理为结构化报告。

### 1.4 产品非目标

第一版不做以下功能：

- 不重新开发通用多智能体框架。
- 不开发独立的大模型 API 网关。
- 不自行提供免费模型服务。
- 不强制要求六个不同模型。
- 不以无限轮自动辩论为核心。
- 不训练或微调六个独立基础模型。
- 不建设云端多用户账户系统。
- 不默认赋予 Bot 修改文件、执行命令或操作外部系统的权限。

## 2. 目标用户与典型使用场景

### 2.1 目标用户

**个人深度思考用户**

希望借助 AI，从多个角度审视自己的问题、计划和选择。

**产品经理与创业者**

希望获得风险分析、创意生成、市场机会分析和商业方案评估。

**研究人员与内容创作者**

希望通过事实审查、批判性分析和创意发散改善内容质量。

**AI Agent 爱好者与开发者**

希望使用多个可定制 Bot，并自由选择底层模型。

### 2.2 典型场景

**场景 A：日常单帽咨询**

用户输入：

`@黑帽 我计划辞职创业，你认为有什么风险？`

系统只调用黑帽。

黑帽执行专用风险分析流程，返回重要风险、成立条件与可验证建议。

**场景 B：多帽联合分析**

用户输入：

`@绿帽 @黄帽 给我一些新产品创意，并分析它们的潜在价值。`

绿帽先提出创新方案，黄帽结合这些方案分析收益和实现条件。

用户可以选择并行独立分析，或让黄帽参考绿帽已完成的输出。

**场景 C：正式六帽会议**

用户输入：

`@蓝帽 组织一次会议，讨论是否应该开发一款 AI 教育产品。`

蓝帽分析议题，提出讨论步骤，由用户确认后启动。

系统逐阶段调用需要的 Bot，最终输出结构化报告。

**场景 D：模型自由组合**

用户可以设置：

- 白帽使用 Kimi
- 红帽使用 Harness 默认模型
- 黑帽使用 Grok
- 黄帽使用 DeepSeek
- 绿帽使用 Gemini
- 蓝帽使用 Harness 默认模型

如果用户只有一个模型，则所有 Bot 共享该模型，但各自执行独立的思考规则。

## 3. 产品差异化与核心创新

### 3.1 创新一：六帽思维引擎

传统多 Bot 工具往往通过简单的人设提示词区分角色。

HexaMind 应将每种思维模式设计为结构化的认知策略。

每个 Bot 内置：

- 角色职责
- 思考步骤
- 主动追问规则
- 禁止行为
- 输出结构
- 自我质量检查
- 可用工具范围

角色策略与模型调用代码分离，允许后续独立迭代。

### 3.2 创新二：人类主蓝帽 + AI 辅助蓝帽

采用双层主持机制。

人类负责目标、权限、审批、流程修改与最终决策。

AI 蓝帽负责议程建议、视角安排、信息整合、重复检测与讨论总结。

所有重大控制动作都应通过程序化权限判断实现，不能仅依赖提示词约束。

### 3.3 创新三：按需召唤，而非强制六帽全部发言

未被提及的 Bot 默认不主动回复。

用户可以自由选择讨论范围。

AI 蓝帽可以建议召唤某个帽子，但未经授权不得擅自展开高成本的多轮讨论。

### 3.4 创新四：自由聊天与结构化会议双模式

**自由 Bot 模式**

突出日常对话、个人咨询、`@` 召唤和多角色交流。

**结构化会议模式**

突出议程、阶段、人工审批、思维切换、结论整理与决策记录。

经典六顶思考帽强调平行思考。产品的自由 Bot 模式属于该方法的创新应用；正式会议模式则应明确阶段性的思维方式，避免简单变成六种人格互相争吵。

### 3.5 创新五：决策工件

系统不仅输出聊天总结，还应输出：

- 当前问题
- 已知事实
- 关键假设
- 情绪与直觉因素
- 风险及应对措施
- 潜在价值
- 替代方案
- 尚未解决的分歧
- 建议验证的事项
- 下一步行动
- 人类最终决定

每个重要条目应尽量能够追溯到原始消息或证据来源。

1. 是否能独立发布为新的插件包。
2. 是否能修改默认 Bot 初始化规则。
3. 是否能独立扩展群聊 UI。
4. 是否能稳定注入六帽专用系统指令。
5. 是否能读取 Harness 当前模型选择。
6. 是否能复用其他插件注册的模型。
7. 是否能为插件分配独立的数据目录和插件 ID。
8. 是否存在无法规避的维护或兼容性问题。

如果这些条件无法合理满足，则使用 Harness 官方插件接口构建轻量独立底座，并仅复用适合的开源代码。

**重要：Fork 之后必须使用独立包名、插件 ID 和数据命名空间，避免与原 DS Bot 同时安装时发生冲突。**

## 5. 功能需求详细说明

### 5.1 六帽 Bot 系统

预置六个固定 Bot：

`white`、`red`、`black`、`yellow`、`green`、`blue`。

每个 Bot 必须具有：

- 不变的内部 ID
- 名称、头像和主题色
- 简短介绍
- 版本化思维策略
- 模型绑定方式
- 独立会话身份
- 可配置记忆
- 工具权限配置
- 独立私聊入口

允许用户修改显示名称和模型，但不得意外破坏系统内部角色 ID。

初次启用插件时执行幂等初始化。

如果六帽已经存在，不得重复创建。

### 5.2 微信式群聊

界面包含：

- 群名称与成员数量
- 六帽成员头像
- 聊天气泡
- 用户消息与 AI 消息区分
- `@` 成员菜单
- Bot 当前模型标识
- 流式回复状态
- 正在思考提示
- 失败与重试提示
- 历史消息滚动
- 讨论暂停与取消入口
- 六帽设置入口

点击 Bot 头像可查看其角色名片。

角色名片包含职责介绍、模型设置、权限和独立聊天入口。

### 5.3 @消息系统

支持：

- `@白帽`
- `@黑帽`
- `@白帽 @绿帽`
- `@全体`
- `@蓝帽`
- 无 @ 的普通消息

默认规则：

- 单个 @：只调用该 Bot。
- 多个 @：按配置进行并行或依次调用。
- @全体：调用六个角色；可由用户选择是否让蓝帽主持。
- 无 @：发送给当前群默认 Bot，初始建议设置为蓝帽。
- @蓝帽：由蓝帽分析请求，必要时提出调度建议。

解析时使用稳定的 Bot ID，不能只依赖字符串替换。

应支持中文、英文别名及输入补全。

必须避免将引用文本或代码块里的 `@` 误判为真实成员召唤。

### 5.4 模型配置

提供两种核心绑定方式。

**模式一：继承 Harness 当前模型**

这是所有帽子的默认设置。

每次开始新的 Bot 调用时，动态读取 Harness 当前有效模型，而不是初始化时复制一次模型 ID。

**模式二：指定模型**

用户从 Harness 已注册模型中选择 Provider 和 Model。

支持原生模型、自定义 API Provider，以及其他插件注册的模型。

如果用户要新增 API Key，引导至 Harness 原生模型配置界面，不自行建立重复的凭据仓库。

模型不可用时展示明确错误信息和重新选择入口。

### 5.5 备用模型和成本策略

支持三个策略：

- 默认策略：优先选定模型，失败时按用户批准的备用列表切换。
- 严格免费：只允许确认符合免费策略的渠道，不明确时停止并询问用户。
- 指定模型：保持用户选定模型，不自动改用其他模型。

不得假设带有“Free”标签的模型永远可用、无限量或不会记录数据。

自动回退不能绕过费用、隐私或用户选择限制。

模型调用日志应记录实际使用的 Provider、Model、是否回退及错误原因。

### 5.6 Bot 记忆

优先复用 DS Bot 已有记忆机制。

记忆分为：

- Bot 私有记忆
- 群聊共享记忆
- 经用户许可的项目背景记忆

系统必须避免无授权的跨私聊信息泄漏。

提供查看、清除和禁用记忆的操作。

第一版不需要新建向量数据库。

### 5.7 讨论执行状态

至少支持：

- `idle`
- `queued`
- `running`
- `awaiting_approval`
- `paused`
- `completed`
- `failed`
- `cancelled`

所有调用需关联唯一 Run ID。

当用户终止讨论时：

- 不再调度新的 Bot。
- 尽量取消正在执行的模型请求。
- 保留已经成功生成的内容。
- 不将取消操作误认为失败。
- 不允许迟到的异步结果重新触发已终止的讨论。

## 6. 六帽思维引擎设计

### 6.1 统一思维策略结构

每个帽子的策略包含：

`identity`：角色身份\
`mission`：职责目标\
`method`：思考步骤\
`constraints`：禁止行为\
`questions`：主动追问条件\
`outputSchema`：输出约定\
`qualityChecks`：质量检查\
`version`：策略版本

系统执行流程：

用户问题 → 构建任务上下文 → 注入帽子策略 → 选择模型 → 执行 → 输出校验 → 呈现结果。

使用结构化的可解释摘要，不要求模型暴露内部隐藏推理过程。

### 6.2 白帽思维策略

**目标：提供可靠的信息基础。**

步骤：

1. 提取关键事实问题。
2. 区分事实、观点和假设。
3. 判断信息是否有来源。
4. 识别未知数据。
5. 给出需要进一步调查的问题。

禁止编造统计数据和来源。

建议输出：

- 已知事实
- 关键证据
- 信息缺口
- 待验证假设

没有联网能力时必须说明不能实时核验。

### 6.3 红帽思维策略

**目标：补充直觉、感受和心理维度。**

步骤：

1. 识别情绪相关因素。
2. 模拟可能出现的用户反应。
3. 寻找不容易量化的直觉风险。
4. 提醒需要进行真实用户验证的地方。

禁止将 AI 预测当成真实用户访谈结果。

建议输出：

- 可能的第一感受
- 情绪与心理影响
- 直觉提醒
- 需要验证的主观因素

### 6.4 黑帽思维策略

**目标：寻找重大风险和失败条件。**

步骤：

1. 识别核心假设。
2. 推导失败场景。
3. 评估风险的可能性和影响。
4. 识别高优先级风险。
5. 给出验证或缓解办法。

禁止没有依据的过度否定。

建议输出：

- 最大风险
- 风险成立条件
- 可能后果
- 优先验证事项
- 防范措施

### 6.5 黄帽思维策略

**目标：寻找价值、收益和可行性。**

步骤：

1. 识别潜在价值。
2. 分析有利条件。
3. 寻找收益来源。
4. 确认收益成立前提。
5. 提出价值实现路径。

禁止只有乐观口号而没有条件分析。

建议输出：

- 潜在收益
- 主要优势
- 成功前提
- 价值验证方式

### 6.6 绿帽思维策略

**目标：创造更多有价值的选择。**

步骤：

1. 重新定义问题。
2. 挑战默认假设。
3. 生成多个不同方向的方案。
4. 组合跨领域思路。
5. 筛选值得验证的创新。

建议输出：

- 新思路
- 与现有方案的差异
- 核心创新点
- 可执行的小型实验

### 6.7 蓝帽思维策略

**目标：管理讨论质量而不是替用户决策。**

步骤：

1. 明确当前目标。
2. 判断适合使用哪些思维模式。
3. 提出合理的讨论顺序。
4. 识别观点重复与缺失。
5. 汇总阶段成果。
6. 向用户建议下一步。

蓝帽必须遵循：

- 不擅自改变用户目标。
- 不绕过用户审批。
- 不无限展开讨论。
- 不把模型观点冒充最终决定。
- 不未经许可执行具有副作用的工具操作。

## 7. 双蓝帽控制系统

### 7.1 权限定义

人类用户为最高主持者。

AI 蓝帽为辅助主持者。

| 操作     | 人类    | AI 蓝帽       |
| ------ | ----- | ----------- |
| 设定讨论目标 | 决定    | 建议          |
| 选择参与角色 | 直接控制  | 建议或在授权范围内调度 |
| 开始下一阶段 | 审批    | 提议          |
| 暂停讨论   | 随时执行  | 依规则执行       |
| 终止讨论   | 随时执行  | 可建议         |
| 修改预算   | 决定    | 不得自行提高      |
| 输出总结   | 审查与修改 | 生成草稿        |
| 执行外部操作 | 审批    | 不得绕过审批      |

### 7.2 会议工作流

第一步：用户输入讨论主题。

第二步：AI 蓝帽生成议程建议。

第三步：用户批准或编辑议程。

第四步：系统调用本阶段相关 Bot。

第五步：收集和整理结果。

第六步：蓝帽分析是否存在遗漏或重复。

第七步：询问用户是否继续、追问、切换帽子或结束。

第八步：生成报告。

第九步：用户确认最终决策记录。

### 7.3 执行预算

初始建议：

- 最大自动讨论轮数：3
- 单轮最多召唤 Bot：6
- 每轮自动接力次数：默认 0
- 最高讨论轮数：由用户配置
- 外部写入工具：默认关闭

必须有循环检测、重复请求去重和费用保护。

## 9. 模型路由与第三方插件兼容

### 9.1 模型选择流程

收到 Bot 请求后：

1. 读取该 Bot 的模型绑定。
2. 如果为继承模式，读取当前 Harness 有效模型。
3. 如果为指定模式，读取指定 Provider 与 Model。
4. 从 Harness 当前模型目录检查模型是否存在。
5. 检查调用权限和必要能力。
6. 依据费用与隐私策略确定是否允许调用。
7. 运行模型并记录实际来源。
8. 调用失败时按用户允许的策略进行处理。

### 9.2 模型切换

用户允许随时修改单个 Bot 的模型设置。

进行中的请求继续使用启动时的模型快照。

新请求使用新的模型绑定。

不得在流式输出中途无提示地替换模型。

历史会话不因更换模型而消失。

### 9.3 免费模型插件

不得将 Our Free Model 作为强制依赖。

检测到相关插件注册的模型时，可以像其他已配置模型一样提供选择。

免费模型是否能使用，由真实调用和上游响应决定。

不得承诺永久、无限或绝对免费的调用。

涉及不同服务商的数据传输，需要提供明确的来源和隐私提示。

## 11. 测试与验收

### 11.1 核心功能测试

至少实现以下自动化用例：

**T01：初始化**

首次启用自动创建六个 Bot。

重复启用不会创建重复角色。

**T02：默认模型继承**

只配置一个可用 Harness 模型。

六个 Bot 均可独立回复。

改变 Harness 当前模型后，继承模式的 Bot 在下一次请求中采用新模型。

**T03：单帽调用**

发送 `@黑帽 测试一下我的计划`。

只有黑帽执行。

**T04：多帽调用**

发送 `@白帽 @绿帽 分析方案`。

两个 Bot 分别执行，消息身份正确。

**T05：无 @消息**

由当前群默认 Bot 处理，不意外调用全部角色。

**T06：思维策略**

黑帽输出风险结构。

白帽区分事实与假设。

绿帽提出可区分的替代方案。

**T07：模型绑定**

黑帽切换模型后，其他帽子的绑定保持不变。

**T08：模型故障**

目标模型不可用时显示错误，不产生虚假的成功消息。

**T09：免费限制**

严格免费模式下，不会静默切换到未知收费或明确收费的模型。

**T10：讨论暂停**

暂停后不得开启新阶段。

**T11：终止讨论**

终止后不得继续调度，也不得因迟到事件恢复运行。

**T12：权限**

只读模式不能通过 Bot 执行写文件或命令操作。

**T13：记忆隔离**

黑帽私聊中的私有信息不会默认泄漏给其他 Bot。

**T14：消息持久化**

重启 Harness 后，聊天记录和 Bot 配置仍然存在。

**T15：模型插件兼容**

其他插件注册的模型可以通过统一目录被发现和选择。

**T16：卸载安全**

禁用或卸载 HexaMind 后，Harness 普通聊天仍然正常。

### 11.2 思维质量测试

建立不少于 20 个初始案例。

覆盖：

- 创业决策
- 产品设计
- 创意生成
- 风险分析
- 个人选择
- 资料评估

对比：

1. 单模型直接回答。
2. 六帽自由 Bot 对话。
3. 结构化六帽讨论。

评估指标：

- 事实错误数量
- 未经验证的结论数量
- 风险覆盖程度
- 创意多样性
- 有效行动建议数量
- 内容重复率
- 模型调用成本
- 用户对决策帮助的评价

测试数据、评分规则和结果应能在仓库中复现。

## 14. 风险与应对

### 风险一：上游项目更新导致兼容性问题

应对：

- 锁定经过测试的版本。
- 隔离上游依赖。
- 使用适配器封装内部 API。
- 记录版本升级的回归测试结果。

### 风险二：Fork 带来维护负担

应对：

- 尽量少修改上游核心逻辑。
- 六帽创新代码单独分层。
- 为重要修改建立测试。
- 保留与上游更新的对比文档。

### 风险三：六个 Bot 产生大量重复内容

应对：

- 限制每个帽子的任务范围。
- 使用结构化输出。
- 控制自动轮次。
- 允许用户按需选择帽子。
- 让蓝帽识别冗余观点。

### 风险四：多模型调用成本失控

应对：

- 默认不自动全员发言。
- 显示真实模型来源。
- 支持预算限制。
- 提供严格免费模式。
- 任何隐式收费升级都需要明确许可。

### 风险五：AI 蓝帽权限过大

应对：

- 在服务端维护审批状态。
- 不将主持权完全交给模型 Prompt。
- 重大操作必须通过程序化权限验证。

### 风险六：思维方法相关知识产权

应对：

- 保留方法论出处说明。
- 不复制官方培训材料。
- 在产品品牌与展示中避免未经授权使用商标。
- 正式发布前完成商标和内容使用审查。

# 附录 B：项目成功的最终判定

当一个普通 DeepSeek Harness 用户安装 HexaMind 后：

无需理解 Agent 架构，不需要创建六套提示词，不需要配置六个模型，就能直接打开六帽群聊。

用户可以自由 @任何帽子，请它使用专门的方法分析问题。

用户也可以按需替换每顶帽子背后的大模型。

面对复杂决策，用户可以召唤 AI 蓝帽组织会议，并且随时保持对议程、预算和结果的最终控制权。

会议结束后，系统不仅提供六种观点，还能生成带有证据、风险、替代方案、未决问题和行动建议的结构化报告。

**最终成功标准不是六个 AI 能同时聊天，而是这套插件能帮助用户更全面、更有条理地思考问题，并对决策形成实际帮助。**

## 交给 Codex 时的建议

不要让 Codex 一次性完成整个项目。先交付 Phase 0 的源码调研、架构决策和最小可运行插件，再分阶段实现，否则很容易出现“界面已经完成，但与 Harness 的真实模型和 Bot 系统无法对接”的问题。

你可以把上面的计划书直接交给 Codex。第一轮开发的验收重点只有三个：插件能正常挂载到 Harness、能通过宿主现有模型完成真实回复、能为不同 Bot 注入独立思维策略。

这三个环节验证成功后，才适合继续投入群聊交互、蓝帽调度与决策报告。
